# Director-first ticket flow

## Нова бізнес-логіка

Основний канал створення заявок у Service Desk AI - кабінет директора.

Базовий сценарій:

1. Директор створює заявку у директорському порталі.
2. Директор вибирає магазин, категорію і описує проблему.
3. Заявка створюється як `source = director_portal`, `status = pending_review`.
4. Адміністратор відкриває заявку, перевіряє категорію та за потреби змінює її.
5. Основна дія адміністратора - `Підтвердити і додати в план`.
6. Система підтверджує заявку і додає її в draft-план наступного робочого тижня за категорією.

## Основний confirm-flow

Для `director_portal` + `pending_review` головна дія:

`Підтвердити і додати в план`

Вона викликає `confirmTicketWithPlanningDecision` з:

- `planningMode = "next_week"`
- `expectedSource = "director_portal"`
- `requireObject = true`
- `requireCategory = true`

Після підтвердження:

- ticket переходить у `assigned`, якщо виконавець уже призначений;
- ticket переходить у `new`, якщо виконавець не призначений;
- заповнюються `admin_confirmed_at` і `confirmed_by_profile_id`;
- пишеться `ticket_history`;
- заявка додається в `work_plan_items`, якщо знайдено план.

## Як визначається виконавець

Поточна реалізація використовує існуючий auto-routing з `autoWorkPlanConfigs`.

Пріоритет:

1. Якщо адмін вручну призначив виконавця і для нього знайдено auto-plan config, заявка йде в його план.
2. Якщо ручного виконавця немає або його не вдалося зіставити з планом, використовується mapping категорії.
3. Якщо mapping не знайдено, заявка підтверджується, але не додається в план, а адміну показується warning.

Known issue: mapping усе ще залежить від тексту категорії/плану. Наступний етап - перевести routing на `category_id` або стабільний `slug`.

## Категорія як основа маршрутизації

Адмін має перевірити категорію перед підтвердженням.

У UI для директорської pending-заявки показується:

- поточна категорія;
- ручний виконавець, якщо він уже призначений;
- preview очікуваного плану/виконавця;
- warning, якщо mapping не знайдено.

## Підтвердити без плану

Другорядна дія:

`Підтвердити без плану`

Вона передає:

`planningMode = "no_plan"`

Після цього:

- ticket підтверджується;
- `work_plan_items` не створюється;
- у `ticket_history` пишеться, що заявку підтверджено без додавання в план;
- адміну показується success message.

Цю дію варто використовувати тільки для нестандартних випадків.

## Відхилення

`Відхилити` лишається danger-дією для `pending_review` директорських заявок.

Вона:

- переводить ticket у `rejected`;
- не створює `work_plan_items`;
- пише `ticket_history`;
- оновлює `/tickets`, `/tickets/[id]`, `/dashboard`, `/director/tickets`.

## AI/Telegram

AI/Telegram лишається legacy/backup flow.

Важливо:

- код AI/Telegram не видаляється;
- confirm у `/ai-tickets` лишається через shared service;
- default `planningMode = "next_week"`;
- стару логіку, яка підтверджувала AI/Telegram без додавання в план, не повертаємо.

## Manual /tickets/new

`/tickets/new` лишається як адмінський резервний сценарій.

На сторінці додано пояснення:

`Основний канал створення заявок - кабінет директора. Ручне створення використовується для винятків.`

Manual create logic у цьому етапі не змінюється.

## Якщо план або mapping не знайдено

Заявка все одно підтверджується.

Адмін бачить warning:

`Заявку підтверджено, але не додано в план. Перевірте категорію або виконавця.`

У `ticket_history` пишеться причина, яку повернув planning helper.
