# Пропозиція нової логіки керування заявками і планами

Дата: 2026-08-09  
Основа: `docs/planning-current-functionality-audit.md` і `docs/admin-actions-and-buttons-audit.md`  
Мета: спростити керування заявками і планами, уніфікувати confirm-flow і зробити поведінку системи передбачуваною для адміністратора.

## 1. Проблеми поточної логіки

1. Є різні confirm-flow для різних сторінок:
   - `/tickets/[id]` після підтвердження викликає додавання в план.
   - `/ai-tickets` підтверджує AI/Telegram заявку окремою логікою і не проходить через той самий planning helper.

2. Адмін не вибирає явно, куди має потрапити підтверджена заявка:
   - поточний тиждень;
   - наступний тиждень;
   - без плану.

3. Зміна виконавця після додавання в план не переносить заявку в план нового виконавця.

4. Зміна категорії після додавання в план не переносить заявку в інший категорійний/виконавчий план.

5. Manual/admin заявки створюються зі status `new`, але не мають єдиного сценарію планування.

6. Планування частково автоматичне, частково ручне, але UI не завжди пояснює, що саме відбулося.

7. Небезпечні дії розкидані по різних місцях:
   - hard delete заявки;
   - видалення плану;
   - скасування плану;
   - видалення item-а з плану;
   - відхилення заявки.

8. `/work-planning` зараз поєднує багато ролей:
   - overview тижнів;
   - створення плану;
   - export;
   - duplicate repeats;
   - перехід до деталей плану.

9. Адмін не завжди бачить, чи заявка вже в плані, у якому саме плані і на який тиждень.

## 2. Кнопки, які дублюють або мають різну логіку

| Дія | Де є зараз | Проблема |
|---|---|---|
| Підтвердити заявку | `/tickets/[id]`, `/ai-tickets` | різна логіка після підтвердження |
| Відхилити заявку | `/tickets/[id]`, `/ai-tickets` | бажано єдиний action і єдиний audit trail |
| Змінити статус | `/tickets/[id]`, quick modal у `/work-planning/[id]` | одна дія доступна в різних місцях |
| Призначити виконавця | `/tickets/[id]`, `/ai-tickets`, quick modal | не вирішує автоматично питання плану |
| Змінити категорію | `/tickets/[id]`, `/ai-tickets`, quick modal | не вирішує автоматично питання плану |
| Надіслати виконавцю | `/tickets/[id]`, plan dispatch у `/work-planning/[id]` | різні сценарії Telegram |
| Видалити заявку | `/tickets`, `/tickets/[id]` | destructive action має бути винесений вниз і мати однаковий confirm |
| Видалити/скасувати план | `/work-planning`, `/work-planning/[id]` | різні рівні ризику мають бути пояснені в UI |

## 3. Дії, які треба уніфікувати

Потрібен єдиний service layer для заявок:

- `confirmTicketWithPlanningDecision(ticketId, decision)`
- `rejectTicket(ticketId, reason?)`
- `changeTicketWorker(ticketId, workerId, planDecision?)`
- `changeTicketCategory(ticketId, categoryId, planDecision?)`
- `changeTicketStatus(ticketId, status)`
- `syncTicketPlan(ticketId, decision)`

UI може бути різним, але всі сторінки мають викликати одну бізнес-логіку.

Уніфікувати треба:

1. Confirm director ticket.
2. Confirm AI/Telegram ticket.
3. Confirm manual/admin ticket, якщо в майбутньому manual заявки теж проходитимуть підтвердження.
4. Reject pending ticket.
5. Assign worker.
6. Change category.
7. Add/move/remove from plan.

## 4. Новий єдиний confirm-flow

### Загальна схема

При натисканні `Підтвердити` адмін має бачити коротке рішення:

1. Перевірити заявку.
2. Вибрати виконавця, якщо потрібно.
3. Вибрати категорію, якщо потрібно.
4. Вибрати планування:
   - `Поточний тиждень`;
   - `Наступний тиждень`;
   - `Без плану`.
5. Підтвердити.

Після submit система:

1. Перевіряє права.
2. Перевіряє source/status.
3. Оновлює ticket:
   - `status = assigned`, якщо є worker;
   - `status = new`, якщо worker немає;
   - confirmation поля, якщо потрібні.
4. Пише `ticket_history`.
5. Виконує planning decision.
6. Повертає success або warning.

### Director tickets

Для `source = director_portal`:

- стартовий status: `pending_review`;
- підтвердження тільки admin/management/tech_manager;
- обов'язкові `object_id` і `category_id`;
- після підтвердження директор бачить людський статус:
  - якщо додано в план: `Додана в план виконання`;
  - якщо без плану: `Підтверджена адміністратором`;
  - якщо rejected: `Відхилена`.

Рекомендована default опція планування: `Наступний тиждень`, якщо заявка не термінова.

### AI/Telegram tickets

Для AI/Telegram:

- стартовий status: `pending_review`;
- підтвердження має йти через той самий confirm service;
- AI confidence, original message і recommended worker залишаються тільки як підказки;
- після підтвердження система не повинна мати окрему логіку, що обходить planning helper.

Рекомендована default опція: `Наступний тиждень`.

Для urgent/high priority можна пропонувати `Поточний тиждень`, але рішення має підтвердити адмін.

### Manual/admin tickets

Є два варіанти.

Варіант A, без зміни моделі:

- manual ticket створюється як `new`;
- після створення адмін бачить Action Panel:
  - `Додати в план`;
  - `Залишити без плану`;
  - `Призначити виконавця`.

Варіант B, більш чистий:

- manual ticket теж створюється через confirm-like step:
  - створити як draft/new;
  - одразу вибрати планування.

Рекомендація для першого етапу: Варіант A, бо він не потребує міграцій.

## 5. Вибір плану при підтвердженні

### Опція 1: Поточний тиждень

Використовувати для термінових або вже погоджених робіт.

Логіка:

1. Взяти current work week через central helper.
2. Переконатись, що draft plan існує.
3. Якщо план поточного тижня вже sent:
   - або не дозволяти автоматично додавати;
   - або показати warning: `План уже надіслано. Додати в чернетку не можна.`
4. Додати item у правильний draft plan.

### Опція 2: Наступний тиждень

Default для більшості заявок.

Логіка:

1. Взяти next work week.
2. Створити/оновити draft plans через існуючу auto draft logic.
3. Додати item у правильний draft plan.

### Опція 3: Без плану

Використовувати, якщо:

- заявка потребує уточнення;
- робота буде виконана поза тижневим планом;
- категорія/виконавець ще не визначені;
- адмін свідомо відкладає планування.

Логіка:

1. Ticket підтверджується.
2. `work_plan_items` не створюється.
3. У `ticket_history` пишеться:
   - `Заявку підтверджено без додавання в план`.
4. На `/tickets/[id]` показати badge:
   - `Не в плані`.

## 6. Зміна виконавця, якщо заявка вже в плані

При зміні worker система має перевіряти, чи ticket уже є в active/draft plan.

Якщо не в плані:

- просто оновити `assignee_worker_id`.

Якщо в плані:

Показати modal:

`Заявка вже додана в план. Що зробити?`

Варіанти:

1. `Перемістити в план нового виконавця`
   - знайти draft plan нового worker-а для того самого тижня;
   - перемістити `work_plan_item`;
   - оновити `work_plan_items.worker_id`;
   - написати history.

2. `Залишити в поточному плані`
   - оновити тільки ticket worker;
   - показати warning, що plan і ticket можуть відрізнятися.

3. `Прибрати з плану`
   - видалити `work_plan_item`;
   - ticket лишається assigned новому worker-у;
   - history.

Default: `Перемістити в план нового виконавця`, якщо target draft plan знайдено.

## 7. Зміна категорії, якщо заявка вже в плані

При зміні category система має перевіряти, чи змінився target plan.

Якщо ticket не в плані:

- просто оновити category.

Якщо ticket у плані:

Показати modal:

`Зміна категорії може змінити план виконавця. Що зробити?`

Варіанти:

1. `Перемістити за новою категорією`
   - знайти target plan за category mapping;
   - перемістити item;
   - оновити `work_plan_items.category`;
   - history.

2. `Залишити в поточному плані`
   - оновити тільки ticket category;
   - залишити item у старому плані;
   - history з note.

3. `Прибрати з плану`
   - видалити item;
   - ticket лишається активним без плану.

Default: `Перемістити за новою категорією`, якщо mapping існує.

## 8. Кнопки, які потрібно залишити на `/tickets/[id]`

У верхньому Action Panel:

- `Підтвердити`;
- `Відхилити`;
- `Змінити статус`;
- `Призначити / змінити виконавця`;
- `Змінити категорію`;
- `Додати в план / змінити план`;
- `Надіслати виконавцю`, якщо worker призначений.

У контенті заявки:

- `Відкрити об'єкт`;
- перегляд фото;
- завантаження фото, якщо роль і статус дозволяють;
- історія;
- акт, якщо є.

## 9. Кнопки, які потрібно прибрати або сховати вниз

Сховати вниз у `Danger zone`:

- `Видалити заявку`;
- `Скасувати заявку`;
- destructive reject для вже підтверджених, якщо такий сценарій буде;
- hard delete фото, якщо буде.

Зробити менш помітними:

- comment actions;
- технічні debug/status details;
- raw AI поля після підтвердження.

Прибрати дублювання:

- confirm/reject не мають повторюватись у кількох блоках однієї сторінки;
- worker/category/status мають бути тільки в одному Action Panel.

## 10. Новий Action Panel на сторінці заявки

Рекомендована структура:

```text
Action Panel

Статус:
[Поточний статус badge]
[select: новий статус] [Зберегти]

Виконавець:
[select worker] [Зберегти]
Якщо заявка в плані: показати "Заявка у плані: ..."

Категорія:
[select category] [Зберегти]
Якщо category впливає на план: показати планову дію

Планування:
[Поточний тиждень] [Наступний тиждень] [Без плану]
[Застосувати]

Pending actions:
[Підтвердити] [Відхилити]
```

Для `pending_review` основний сценарій:

```text
Перевірити заявку
1. Категорія
2. Виконавець
3. Планування
4. Підтвердити
```

Після підтвердження confirm/reject зникають, лишається керування status/worker/category/plan.

## 11. Спрощена сторінка `/work-planning`

Зробити `/work-planning` як зрозумілий центр тижнів:

1. Три головні вкладки:
   - `Поточний тиждень`;
   - `Наступний тиждень`;
   - `Архів`.

2. На кожному тижні:
   - cards планів виконавців;
   - count заявок;
   - count без виконавця;
   - count не виконано;
   - status плану.

3. Primary buttons:
   - `Створити / оновити чернетки`;
   - `Експорт тижня`;
   - `Надіслати плани`, якщо всі готові.

4. Secondary:
   - duplicate repeats;
   - manual create plan;
   - filters.

5. Детальні дії item-а лишити у `/work-planning/[id]`.

## 12. Destructive actions

Винести вниз і завжди підтверджувати:

| Дія | Де | Confirm text |
|---|---|---|
| Видалити заявку | `/tickets/[id]` bottom danger zone | `Ви точно хочете повністю видалити заявку? Цю дію не можна скасувати.` |
| Відхилити pending заявку | верх pending panel | `Відхилити заявку? Директор або AI-flow побачить статус відхилення.` |
| Видалити план | `/work-planning/[id]` danger zone | `Видалити план? Заявки залишаться у системі без цього плану.` |
| Скасувати план | `/work-planning/[id]` danger zone | `Скасувати чернетку плану?` |
| Прибрати item з плану | item menu | `Прибрати заявку з плану? Заявка залишиться активною.` |
| Resend all Telegram | `/work-planning/[id]` | `Надіслати план повторно всім виконавцям?` |

## 13. Що можна зробити без міграцій

1. Створити єдиний server-side service для confirm-flow.
2. Перевести `/ai-tickets` на цей service.
3. Додати planning decision через form fields/query params.
4. Додати modal для зміни worker/category, якщо ticket уже в плані.
5. Додати UI badge:
   - `У плані`;
   - `Не в плані`;
   - `План: ...`;
   - `Тиждень: ...`.
6. Додати warning-и без нових колонок.
7. Уніфікувати Action Panel на `/tickets/[id]`.
8. Спрощено перегрупувати `/work-planning`.
9. Використовувати існуючі `work_plan_items`, `ticket_history`, `work_plans`.
10. Додати code-level duplicate protection у межах тижня.

## 14. Що може потребувати міграцій

Не обов'язково для першого етапу, але корисно пізніше:

1. `tickets.planning_status`
   - `not_planned`, `planned`, `planning_skipped`, `planning_failed`.

2. `tickets.planned_at`
   - коли заявка вперше потрапила в план.

3. `tickets.planning_decision`
   - `current_week`, `next_week`, `no_plan`.

4. `work_plan_items.source`
   - `confirm_flow`, `manual`, `carry_over`, `telegram_auto`.

5. Unique constraint на одну заявку в одному робочому тижні:
   - складніше, бо треба врахувати `work_plans.period_start/period_end`;
   - перед цим треба перевірити старі дублікати.

6. `categories.slug` або стабільний `planning_key`
   - щоб перейти з mapping по тексту на стабільний ключ.

7. `work_plans.worker_id`
   - щоб план явно належав worker-у, а не визначався назвою.

## 15. Безпечний план реалізації

### Етап 1. Уніфікувати підтвердження і планове рішення

Без міграцій.

Зробити:

1. Створити service:
   - `confirmTicketWithPlanningDecision`.
2. Підключити його до:
   - director confirm;
   - generic confirm;
   - AI confirm.
3. Додати planning decision:
   - current week;
   - next week;
   - no plan.
4. Додати warnings:
   - plan not found;
   - category has no mapping;
   - worker has no draft plan;
   - already planned.
5. Зберегти поточну поведінку default:
   - director/AI default: next week;
   - якщо треба сумісність, тимчасово default як зараз.

Результат: усі заявки підтверджуються однаково.

### Етап 2. Новий Action Panel на `/tickets/[id]`

Без міграцій.

Зробити:

1. Один блок `Що зробити?`.
2. Confirm/reject тільки для pending.
3. Worker/category/status в одному місці.
4. Planning controls в одному місці.
5. Badge `У плані` з назвою плану.
6. Danger zone внизу.

Результат: адмін бачить один центр керування заявкою.

### Етап 3. Синхронізація worker/category з планом

Можна без міграцій.

Зробити:

1. При зміні worker перевіряти active plan item.
2. Показувати modal:
   - move;
   - keep;
   - remove from plan.
3. При зміні category робити те саме.
4. Писати history.

Результат: менше розсинхрону між ticket і plan.

### Етап 4. Спрощення `/work-planning`

Без міграцій для UI.

Зробити:

1. Вкладки: current / next / archive.
2. Primary action: create/update drafts.
3. Export і send винести в зрозумілий action row.
4. Manual create plan сховати в secondary flow.
5. Детальні item actions лишити у plan detail.

Результат: planning page стає менш перевантаженою.

### Етап 5. Стабільні mapping-и і DB-покращення

Може потребувати міграцій.

Зробити:

1. `categories.planning_key` або `slug`.
2. `work_plans.worker_id`.
3. Planning status fields на ticket.
4. Stronger duplicate protection.

Результат: менше залежності від текстових назв і назви плану.

## 16. Рекомендований етап 1

Почати з уніфікації confirm-flow.

Чому:

- це найвищий бізнес-ризик;
- зараз AI і `/tickets/[id]` можуть поводитись по-різному;
- director flow уже близький до правильної логіки;
- можна зробити без міграцій;
- це створить основу для нового Action Panel.

Мінімальний результат етапу 1:

- один helper/service для confirm;
- всі pending sources проходять через нього;
- адмін вибирає current week / next week / no plan;
- warning-и структуровані;
- history однакова.

## 17. Рекомендований етап 2

Після service layer переробити `/tickets/[id]`.

Ціль:

- один Action Panel;
- менше дублювання кнопок;
- планування видно прямо в заявці;
- destructive actions внизу.

Це дасть адмінам зрозумілий інтерфейс без різних сценаріїв у різних частинах сторінки.

## 18. Що не чіпати поки що

1. Не змінювати DB schema на першому етапі.
2. Не видаляти існуючі work plans.
3. Не змінювати RLS без окремого аудиту.
4. Не чіпати mobile app.
5. Не переписувати Telegram bot.
6. Не міняти reports/export, поки не стабілізовано core planning service.
7. Не робити hard migration category mapping до завершення тестів.

## 19. Ризики

1. Якщо одразу змінити confirm-flow для AI, можна змінити очікувану поведінку Telegram-відправки.
2. Якщо додавати current week planning, треба чітко вирішити, чи можна додавати в уже sent plan.
3. Якщо переміщувати item при зміні worker/category, можна зачепити dispatch history.
4. Якщо зробити `no plan`, треба не загубити такі заявки у списку.
5. Якщо mapping лишиться по `category.name`, перейменування категорій і далі буде ризиком.
6. Якщо не додати UI badge `Не в плані`, адмін може думати, що підтверджена заявка автоматично запланована.
7. Якщо змішати service refactor і UI redesign в одному етапі, буде важко тестувати.

## 20. Коротке цільове правило

Кожна заявка після створення має мати зрозумілий стан:

- `Очікує перевірки`;
- `Підтверджена, але не в плані`;
- `Підтверджена і додана в план`;
- `Передана виконавцю`;
- `В роботі`;
- `Очікує підтвердження виконання`;
- `Виконана`;
- `Відхилена`.

Адмін при кожній ключовій зміні має бачити не тільки зміну ticket, а й наслідок для плану.
